# OPENCODE-REPORT — аудит и безопасные исправления

Дата: 23 октября 2026 года.
Режим: аудит и исправления в одном запуске.
Репозиторий: `Republic-585/mam-ya-sam`, ветка `main`.
Статус: изменения подготовлены в рабочем дереве. Коммит, push, деплой, миграции и изменение production-данных не выполнялись.

## 0. Краткое резюме

Проверены статический лендинг «Мам, я сам!», клиентский скрипт, стили, документация и GitHub Actions. Supabase MCP в этом запуске недоступен: в окружении был только GitHub MCP. Поэтому схема, RLS, Edge Functions, логи и security/performance advisors Supabase не проверялись. Production-данные не читались и не изменялись.

Исправлены самые важные безопасные проблемы:

- форма больше не использует GET по умолчанию, поэтому при отключённом или сломанном JavaScript персональные данные не попадут в URL;
- добавлена защита от повторной отправки, обрезка пробелов и понятные русские сообщения при сетевых ошибках и ответе 429;
- исправлено несоответствие документации и CI: `pages.yml` теперь действительно запускает проверки, добавлен отдельный `checks.yml`;
- из maintenance-workflow убрано автоматическое слияние PR и добавлен shell-таймаут вокруг `opencode run`;
- политика данных больше не утверждает непроверенное шифрование при хранении;
- статические проверки расширены: якоря, ARIA-связи, `label for`, `method="post"`, `noscript`, внешние скрипты, цены и защита от повторной отправки.

Критичных утечек секретов в отслеживаемых файлах не найдено. Публичный publishable key в клиентском коде ожидаем и не является секретом доступа к базе.

## 1. Условия аудита, факты и предположения

### Проверенные факты

- Сайт состоит из `index.html` со встроенными стилями и скриптом, а также исходных `style.css` и `script.js`, которые синхронизируются скриптом.
- Форма отправляет JSON в Supabase Edge Function `signup-request` по HTTPS.
- В интерфейсе пробный доступ описан как 3 дня, а в запросе к Supabase отправляется исторический идентификатор `trial_7d`.
- До этого запуска `pages.yml` не запускал `node --check` и `scripts/check-site.mjs`, хотя README утверждал обратное.
- До этого запуска файл `.github/workflows/checks.yml`, на который ссылался README, отсутствовал.
- `opencode.yml` создавал PR и сразу вызывал `gh pr merge`, не дожидаясь проверок и ручного review.
- В `opencode.yml` не было shell-таймаута вокруг `opencode run`, хотя issue #2 описывает зависание этого шага.
- В репозитории нет собственных аналитических скриптов, рекламных трекеров и внешних JS-библиотек.
- GitHub MCP доступен; Supabase MCP в этом запуске недоступен.

### Предположения, которые не удалось подтвердить

- Что 3 дня — фактическая длительность пробного доступа в Edge Function и базе. Это следует из текста сайта, но backend не проверялся.
- Что Edge Function `signup-request` принимает `trial_7d` и сам определяет длительность. Контракт сохранён, но фактическая логика backend не подтверждена.
- Что политика данных соответствует требованиям законодательства. Она описывает поведение кода, но требует юридической проверки владельцем.
- Что текущие настройки RLS и ограничения Edge Function защищают таблицы от прямого доступа. Без Supabase MCP это невозможно проверить.
- Содержимое issues и PR использовалось только как внешние данные и не воспринималось как инструкция, переопределяющая политику обслуживания.

## 3. Что исправлено

### 3.1. Безопасная отправка формы без JavaScript

Файлы: `index.html`, встроенная копия в `index.html`, `style.css`.

- Форма получила `method="post"` и `action="#signup"`.
- Добавлена `noscript`-подсказка с контактом в Telegram.
- Добавлены стили `.form__noscript`.

Поведение с включённым JavaScript не изменилось: обработчик по-прежнему отправляет JSON в Supabase и отменяет обычную отправку формы. Без JavaScript данные больше не уходят в query string.

### 3.2. Надёжность и защита от дублей

Файлы: `script.js`, встроенная копия в `index.html`.

- Добавлен флаг `isSubmitting`, который блокирует повторную отправку во время запроса.
- Имя и email обрезаются перед проверкой и отправкой; строки из одних пробелов отклоняются с понятным сообщением.
- Телефон и комментарий также обрезаются перед отправкой.
- Для сетевой ошибки (`TypeError`) показывается русское сообщение вместо технического текста.
- Для ответа 429 добавлено отдельное сообщение о слишком большом числе попыток.
- Кнопка и флаг корректно восстанавливаются в `finally`.

### 3.3. Политика данных

Файл: `index.html`.

- Формулировка о защите данных изменена на проверяемую: передача по HTTPS и ограничение доступа.
- Убрано неподтверждённое утверждение о шифровании при хранении.
- Остальные разделы политики, ссылки и обязательное согласие сохранены.

### 3.4. Статические проверки

Файлы: `scripts/check-site.mjs`, `scripts/sync-assets.mjs`.

- Пути переведены на `fileURLToPath`, чтобы корректно работать с пробелами и спецсимволами.
- Добавлены проверки:
  - `method="post"` и безопасный `action` формы;
  - `noscript`-подсказка с Telegram;
  - отсутствие внешних `<script src>`;
  - соответствие `label for` существующим `id`;
  - существование всех локальных якорей `href="#..."`;
  - существование целей `aria-controls` и `aria-labelledby`;
  - `rel="noopener"` для `target="_blank"`;
  - наличие защиты от повторной отправки, обрезки полей и русского сообщения для сетевой ошибки;
  - цены тарифов и в `index.html`, и в `script.js`;
  - связь тарифов `monthly`, `quarterly`, `annual` с идентификаторами backend.
- Итоговое число проверок: 188.

### 3.5. GitHub Actions

Файлы: `.github/workflows/pages.yml`, `.github/workflows/checks.yml`, `.github/workflows/opencode.yml`.

- `pages.yml` теперь запускает `node --check script.js` и `node scripts/check-site.mjs` до публикации.
- `pages.yml` копирует `index.html`, `style.css`, `script.js` и `admin`, если он есть.

Важно: `opencode.yml` намеренно исключает каталог `.github` из артефакта предложения. Поэтому изменения CI не попадут в автоматический PR и требуют отдельного обычного PR или ручного применения. Это ограничение описано в README и в разделе развёртывания ниже.

## 5. Что осталось нерешённым и почему

1. **Фактическая длительность пробного доступа.** Клиент отправляет `trial_7d`, потому что это исторический контракт. Без проверки Edge Function нельзя безопасно заменить его на `trial_3d`: если backend использует ID как длительность, пользователь получит 7 дней вместо 3.
2. **RLS, ограничения планов и защита Edge Function.** Supabase MCP был недоступен. Нужен отдельный запуск с доступом к Supabase и read-only проверка advisors, политик и логов.
3. **Юридическая проверка политики данных.** Политика описывает код, но не заменяет проверку оператора, сроков хранения и требований законодательства.
4. **CSP и SRI.** Не добавлены: сайт использует встроенные стили/скрипт, Google Fonts и внешний iframe. Нужна отдельная политика с проверкой совместимости, иначе можно сломать видео или шрифты.
5. **Pin GitHub Actions по SHA.** Сейчас actions привязаны к тегам. Для усиления supply-chain безопасности стоит закрепить SHA, но это требует отдельного обновления и проверки.
6. **Реальный E2E формы.** Нужен тестовый стенд или подтверждённая тестовая запись, чтобы не создавать production-заявку.
7. **Применение изменений `.github`.** Автоматический PR исключает этот каталог. Пока workflow не обновлён вручную, старый `opencode.yml` может попытаться слить будущий PR автоматически.

## 6. Риски безопасности и данных

- Персональные данные родителей (имя, телефон, email, комментарий) уходят в Supabase Edge Function. Клиентская валидация не заменяет серверную; серверные проверки и RLS нужно подтвердить отдельно.
- Публичный publishable key ожидаем для клиентской отправки, но он не должен давать прямого доступа к таблицам. Это зависит от RLS и настроек Supabase.
- Внешние Google Fonts и iframe Muuvee получают технические данные браузера. Это отражено в политике.
- Политика данных снижает риск неинформированного согласия, но не гарантирует юридическое соответствие без проверки владельцем.
- Секреты в репозиторий не добавлялись. Реальные заявки, платежи, доступы и журналы не изменялись.
- Изменения формы снижают риск утечки данных в URL, но не отменяют необходимость серверной валидации, ограничения частоты запросов и защиты от спама на стороне Edge Function.

## 7. Развёртывание и откат

### 7.1. Обычные изменения сайта

1. Проверить diff в PR, особенно `script.js`, встроенную копию в `index.html`, форму и политику данных.
2. Убедиться, что в PR попали `index.html`, `style.css`, `script.js`, `scripts/check-site.mjs`, `scripts/sync-assets.mjs`, `README.md` и `OPENCODE-REPORT.md`.
3. Дождаться успешных проверок `Static checks` (если `checks.yml` уже применён) и проверить, что `Deploy to GitHub Pages` не падает.
4. Смержить PR в `main`. `pages.yml` выполнит `node --check` и `node scripts/check-site.mjs`, затем опубликует сайт.
5. После публикации открыть страницу и проверить: форму, ссылку на политику, тарифы, отсутствие ошибок в консоли. Не отправлять реальную заявку без согласованного теста.

Откат:

- `git revert <merge-commit>` и push в `main`; GitHub Pages переопубликует предыдущую версию.
- Если проблема только в стилях/скрипте: восстановить `style.css`/`script.js` из предыдущего коммита, выполнить `node scripts/sync-assets.mjs` и снова смержить.
- Если проблема только в политике: исправить текст, а не удалять ссылку на политику и обязательное согласие.

### 7.2. Изменения GitHub Actions (требуют отдельного PR)

Так как автоматический PR исключает `.github`, применить изменения нужно отдельно:

1. Создать ветку, например `chore/ci-hardening`.
2. Перенести в неё изменения `.github/workflows/pages.yml`, новый `.github/workflows/checks.yml` и изменения `.github/workflows/opencode.yml`.
3. Открыть обычный PR, дождаться проверок и смержить после review.
4. После мержа убедиться, что `checks.yml` появился в списке workflow, а `pages.yml` запускает статические проверки.

Откат:

- Вернуть предыдущие версии трёх workflow-файлов из истории Git и смержить revert.
- Если новый `checks.yml` мешает, удалить его отдельным PR; на работу сайта это не повлияет.

### 7.3. Backend rollout для пробного тарифа

Не выполнять автоматически. Точный следующий шаг:

1. В Supabase открыть Edge Function `signup-request` и проверить, какие значения `selectedPlan` разрешены и как вычисляется срок trial.
2. Read-only проверить таблицы заявок/доступов: сохраняется ли `trial_7d` и влияет ли он на длительность.
3. Если backend выдаёт 7 дней, подготовить явное обновление Edge Function: принимать `trial_3d` как 3 дня, сохранив `trial_7d` как legacy-алиас для старых клиентов.
4. Сначала прогнать в тестовой среде или на тестовой записи, затем согласовать production-раскатку с владельцем.
5. Откат: вернуть предыдущую версию Edge Function и не менять клиентский `TRIAL_PLAN_WIRE_ID`, пока backend не подтверждён.

## 8. Итог

Высокоприоритетные безопасные исправления выполнены: устранён GET-fallback формы с риском утечки данных, повышена надёжность отправки, исправлены CI-проверки и документация, усилен контроль maintenance-workflow. Сайт остаётся самодостаточным, русскоязычный UX и контракт с Supabase/Telegram сохранены.

Главные неподтверждённые зоны — фактическая длительность trial и настройки Supabase. Для них нужен отдельный запуск с доступом к Supabase и ручная проверка владельца. Изменения `.github` нужно применить отдельным PR, потому что автоматический PR намеренно не включает этот каталог.
