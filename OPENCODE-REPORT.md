Дата: 23 октября 2026 года.
Режим: аудит + исправления в одном запуске.
Репозиторий: `Republic-585/mam-ya-sam`, ветка `main`.
Автоматический деплой и миграции не выполнялись, коммит и push не делались.

## 0. Краткое резюме

Проверен статический сайт «Мам, я сам!»: `index.html`, `script.js`, `style.css`, документация и GitHub Actions. Supabase MCP в этом запуске был недоступен, поэтому схема, RLS, Edge Functions, логи и advisors Supabase не проверялись. Production-данные не читались и не изменялись.

Исправлены самые важные безопасные проблемы:

- Telegram-редирект теперь использует только проверенный URL;
- устранена путаница `trial_7d` / «3 дня» на уровне интерфейса и кода, при этом идентификатор в запросе к Supabase сохранён для совместимости;
- у отправки формы появился таймаут и корректное восстановление кнопки;
- добавлена политика обработки персональных данных и ссылки на неё;
- добавлены статические проверки и синхронизация встроенных стилей/скрипта;
- заполнен README и снижен риск зависания maintenance-workflow.

Критичных утечек секретов в отслеживаемых файлах не найдено. Публичный publishable key в клиентском коде ожидаем и не является секретом доступа к базе.

## 1. Условия аудита и различия фактов и предположений

Проверенные факты:

- сайт состоит из одного `index.html` со встроенными стилями и скриптом, а также копий `style.css` и `script.js`;

Предположения, которые не удалось подтвердить в этом запуске:

- что 3 дня — правильная длительность пробного доступа. Это следует из текста сайта, но не проверено в Edge Function или базе;
- что Edge Function `signup-request` принимает `trial_7d` и сам определяет длительность доступа. Контракт сохранён, но backend не проверялся;
- что политика данных соответствует юридическим требованиям владельца. Она описывает фактическое поведение кода, но требует юридической проверки;

## 3. Что исправлено

### 3.1 Безопасность Telegram-редиректа

Файлы: `script.js`, встроенная копия в `index.html`.

- добавлена константа `TRIAL_PLAN_WIRE_ID = 'trial_7d'`;
- оба успешных сценария теперь делают переход только по проверенному `telegramUrl`;
- `safeTelegramUrl` по-прежнему разрешает только `https://t.me` и `https://telegram.me`;
- добавлены проверки, что в коде нет редиректа по `result.telegramUrl`.

Поведение для пользователя не изменилось: после успешной заявки открывается тот же Telegram-бот.

### 3.2 Согласованность пробного тарифа

Файлы: `index.html`, `script.js`, `README.md`.

- интерфейсные ключи `data-plan` и `data-plan-card` переименованы в `trial_3d`;
- внутри `details` ключ `trial_3d` связан с `wireId: TRIAL_PLAN_WIRE_ID`;
- в Supabase по-прежнему отправляется `trial_7d`, поэтому текущий контракт Edge Function не ломается;
- добавлено нормализующее преобразование `trial_7d -> trial_3d` для старых значений и совместимости;

Это исправляет путаницу в клиентском коде, но не подтверждает фактическую длительность доступа в Supabase.

### 3.3 Надёжность формы

## 5. Что осталось нерешённым и почему

1. **Длительность пробного доступа на backend.** Нельзя безопасно менять `trial_7d` на `trial_3d` в запросе без проверки Edge Function и базы. Сейчас клиент отправляет прежний ID, поэтому контракт не ломается. Нужно проверить, сколько дней фактически выдаёт backend, и при необходимости сделать явную миграцию/алиас.
2. **RLS, ограничения планов и защита Edge Function.** Supabase MCP был недоступен. Нужен отдельный запуск с доступом к Supabase для проверки RLS, прав Edge Function, лимитов и логов.
3. **Юридическая проверка политики данных.** Политика описывает код, но не заменяет проверку оператора, сроков хранения и требований законодательства.
4. **CSP и SRI.** Не добавлены, потому что сайт использует встроенные стили/скрипт, Google Fonts и iframe Muuvee. Нужна отдельная политика с проверкой совместимости.
5. **Pin GitHub Actions по SHA.** Сейчас actions привязаны к тегам (`@v4`, `@v5`). Это распространённая практика, но для усиления supply-chain безопасности стоит закрепить SHA.
6. **Реальный E2E формы.** Требуется тестовый стенд или подтверждённая тестовая запись, чтобы не создавать production-заявку.

## 6. Риски безопасности и данных

- Персональные данные родителей (имя, телефон, email, комментарий) уходят в Supabase Edge Function. Клиентская валидация не заменяет серверную; серверные проверки и RLS нужно подтвердить отдельно.
- Публичный publishable key ожидаем для клиентской отправки, но он не должен давать прямого доступа к таблицам. Это зависит от RLS и настроек Supabase.
- Внешние Google Fonts и iframe Muuvee получают технические данные браузера. Это отражено в политике.
- Политика данных снижает риск неинформированного согласия, но не гарантирует юридическое соответствие без проверки владельцем.
- Секреты в репозиторий не добавлялись. Реальные заявки, платежи и доступы не изменялись.

## 7. Развёртывание и откат

### Развёртывание

1. Проверить diff в PR, особенно `script.js`, встроенную копию в `index.html` и раздел политики.
2. Убедиться, что в PR попали `scripts/check-site.mjs`, `scripts/sync-assets.mjs`, `README.md` и `OPENCODE-REPORT.md`.
3. Если process предложения PR исключает `.github`, отдельно применить `checks.yml`, обновлённый `pages.yml` и таймаут в `opencode.yml`. Сайт работает и без этого.
4. Смержить PR в `main`. Workflow `Deploy to GitHub Pages` выполнит `node --check` и `node scripts/check-site.mjs`, затем опубликует сайт.
5. После публикации открыть страницу, проверить тарифы, ссылку на политику и отсутствие ошибок в консоли. Не отправлять реальную заявку без согласованного теста.

### Откат

- Изменения не затрагивают базу данных, платежи, доступы и Edge Functions, поэтому откат данных не требуется.
- Откатить PR через `git revert <merge-commit>` и push в `main`; GitHub Pages переопубликует предыдущую версию.
- Если проблема только в стилях/скрипте: восстановить `style.css`/`script.js` из предыдущего коммита, выполнить `node scripts/sync-assets.mjs` и снова смержить.
- Если проблема только в политике: убрать ссылки и раздел `#privacy-policy`, но это ухудшит информирование о данных; лучше исправить текст.

### Backend rollout для trial

Не выполнять автоматически. Точный следующий шаг:

1. В Supabase проверить Edge Function `signup-request`: какие значения `selectedPlan` разрешены и как вычисляется срок trial.
2. Проверить таблицы заявок/доступов: сохраняется ли `trial_7d` и влияет ли он на длительность.
3. Если backend выдаёт 7 дней, подготовить явную миграцию/обновление Edge Function на 3 дня с обратной совместимостью по `trial_7d`.
4. Сначала прогнать в тестовой среде или на тестовой записи, затем согласовать production-раскатку и откат с владельцем.
