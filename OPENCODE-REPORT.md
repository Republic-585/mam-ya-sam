# OPENCODE-REPORT — аудит и безопасные исправления

Дата: 23 октября 2026 года.
Режим: аудит и исправления в одном запуске.
Репозиторий: `Republic-585/mam-ya-sam`, ветка `main`.
Автоматический деплой, миграции, коммит и push не выполнялись.

## 0. Краткое резюме

Проверены статические файлы сайта «Мам, я сам!»: `index.html`, `script.js`, `style.css`, `README.md`, документация в `content/` и GitHub Actions. Supabase MCP в этом запуске недоступен, поэтому схема, RLS, Edge Functions, логи и advisors Supabase не проверялись. Production-данные не читались и не изменялись.

Исправлены самые важные безопасные и проверяемые проблемы:

- форма больше не может отправить персональные данные методом GET в URL при отключённом или сломанном JS;
- возвращена нативная валидация браузера, усилена защита от повторной отправки;
- технические ошибки сети больше не показываются пользователю по-английски;
- Telegram-редирект дополнительно отклоняет URL с логином, паролем и нестандартным портом;
- добавлена meta-политика referrer и `noreferrer` для внешней ссылки на Telegram;
- добавлены автоматические проверки для формы, ошибок и Telegram-ссылки;
- подготовлены `checks.yml` и обновлённый `pages.yml`, чтобы проверки запускались до публикации;
- добавлен shell-таймаут вокруг `opencode run`, чтобы maintenance-workflow не зависал до общего лимита;
- README приведён в соответствие с фактическим поведением проекта.

Критичных утечек секретов в отслеживаемых файлах не найдено. Публичный publishable key в клиентском коде ожидаем и не даёт доступа к базе без RLS и Edge Function.

Отдельно подчёркиваю: изменения в каталоге `.github` подготовлены в рабочем дереве, но текущий workflow предложения PR исключает `.github` из артефакта. Их нужно применить отдельным обычным PR или вручную по инструкции из раздела 7.

## 1. Условия аудита: факты и предположения

### 1.1 Проверенные факты

- Сайт состоит из самодостаточного `index.html` со встроенными стилями и скриптом, а также исходных `style.css` и `script.js`, которые синхронизируются скриптом `scripts/sync-assets.mjs`.
- Форма отправляет JSON в Supabase Edge Function `signup-request`; в клиенте используется публичный publishable key.
- В интерфейсе пробный тариф называется `trial_3d` и описан как 3 дня, а в запросе к backend по-прежнему отправляется исторический идентификатор `trial_7d` (`TRIAL_PLAN_WIRE_ID`).
- До исправления форма имела `novalidate` и не имела `method`, то есть при отключённом JS браузер мог отправить её методом GET с персональными данными в строке запроса.
- До исправления `safeTelegramUrl` проверял протокол и домен, но пропускал URL с логином, паролем и нестандартным портом.
- До исправления при сетевой ошибке пользователь мог увидеть исходный английский текст исключения вместо русского сообщения.
- В репозитории не было `checks.yml`, хотя README и предыдущий отчёт утверждали, что проверки на push и pull request настроены.
- `pages.yml` до исправления копировал только `index.html` и каталог `admin` и не запускал статические проверки перед публикацией.
- В `opencode.yml` до исправления не было shell-таймаута вокруг `opencode run`; ограничение было только на уровне шага и задания.
- Реальные заявки, платежи, доступы и журналы в репозитории не хранятся.
- В открытых issue нет инструкций, которые могут отменять политику обслуживания; issue использованы только как внешние данные.

### 1.2 Предположения, которые не подтверждены

- Что 3 дня — фактическая длительность пробного доступа в Edge Function и базе. Это следует из текста сайта, но backend в этом запуске недоступен.
- Что Edge Function принимает `trial_7d` и сама определяет длительность доступа, а не трактует идентификатор как «7 дней».
- Что RLS, ограничения таблиц и серверная валидация Edge Function настроены корректно.
- Что политика обработки данных соответствует требованиям законодательства и фактическим срокам хранения у оператора.
- Что видео Muuvee не зависит от дополнительных доменов, которые пришлось бы разрешать в CSP.
- Что maintenance-workflow зависал именно на `opencode run`, а не на другом шаге. Issue #2 использована как внешние данные, а не как инструкция; воспроизвести зависание в этом запуске невозможно.

## 3. Что исправлено

### 3.1 Приватность и надёжность формы

Файлы: `index.html`, `script.js`, `scripts/check-site.mjs`.

- форма переведена на `method="post"`; при отключённом JS данные больше не попадают в query string;
- удалён `novalidate`, поэтому нативная валидация `required` и `type="email"` работает даже без JS;
- добавлен флаг `submitting`, который блокирует повторную отправку до завершения запроса;
- на время запроса форма получает `aria-busy="true"`, после завершения признак снимается;
- добавлен отдельный класс `SignupError`; пользователю показываются только заранее подготовленные русские сообщения, а неизвестные сетевые ошибки заменяются общим русским текстом;
- ответы `429` и `please_wait` обрабатываются как просьба подождать, ответы `400`/`422` — как ошибка заполнения;
- проверка добавлена в `scripts/check-site.mjs`, чтобы форма не вернулась к GET или `novalidate`.

Поведение для пользователя сохранено: форма по-прежнему отправляет те же поля в тот же Edge Function.

### 3.2 Безопасность Telegram-редиректа

Файлы: `script.js`, встроенная копия в `index.html`, `scripts/check-site.mjs`.

- `safeTelegramUrl` теперь дополнительно отклоняет URL с логином, паролем и нестандартным портом;
- по-прежнему разрешены только `https://t.me` и `https://telegram.me`;
- редирект выполняется только по проверенному `telegramUrl`, а не по исходному значению из ответа;
- в проверки добавлены случаи с `user:pass@` и портом `8443`.

### 3.3 Автоматические проверки

Файлы: `.github/workflows/checks.yml` (новый), `.github/workflows/pages.yml`, `scripts/check-site.mjs`.

- `checks.yml` запускает `node --check script.js` и `node scripts/check-site.mjs` на push в `main`, на pull request и вручную;
- `pages.yml` теперь ставит Node.js 20, запускает те же проверки до подготовки сайта и копирует `index.html`, `style.css`, `script.js` и `admin`, если он появится;
- при падении проверок публикация не выполняется;
- добавлены статические проверки: метод формы, отсутствие `novalidate`, безопасный referrer, защита от повторной отправки, `aria-busy`, русские пользовательские ошибки, новые ограничения Telegram-ссылки.

Важно: `.github` исключён из артефакта текущего maintenance-workflow. Поэтому эти файлы подготовлены в рабочем дереве, но не попадут в автоматически создаваемый PR. Точные действия описаны в разделе 7.

### 3.4 Maintenance-workflow

Файл: `.github/workflows/opencode.yml`.

- `opencode run` обёрнут в `timeout --signal=TERM --kill-after=30s 840`;
- это даёт диагностируемый код выхода вместо ожидания полного `timeout-minutes`;
- из артефакта дополнительно исключены `.env`, `.env.*`, `*.pem` и `*.key`, чтобы случайно созданные локальные файлы с секретами не попадали в предложение PR.

### 3.5 Документация и мелкие улучшения

Файлы: `README.md`, `index.html`.

- README теперь точно описывает метод формы, защиту от повторной отправки, обработку ошибок и состав публикации;
- добавлена meta-политика `strict-origin-when-cross-origin`;
- ссылка на Telegram-бот в политике получила `rel="noopener noreferrer"`;
- удалён косметический дефект `\n\n` в комментарии `script.js`;
- встроенные стили и скрипт в `index.html` синхронизированы с исходниками.

### 3.6 Что намеренно не менялось

- Пробный тариф в запросе оставлен `trial_7d`: без проверки Edge Function и данных его нельзя безопасно переименовать, иначе можно сломать существующий контракт.
- Платёжные, ученические, родительские и иные production-данные не читались и не изменялись.
- RLS, авторизация, согласие и серверная валидация не ослаблялись.
- Публичный publishable key не считается секретом и не ротировался.
- Дизайн, русскоязычный UX и Telegram/Supabase-контракт сохранены.

## 5. Что осталось нерешённым и почему

1. **Длительность пробного доступа на backend.** Клиент по-прежнему отправляет `trial_7d`, чтобы не сломать контракт. Нужно проверить Edge Function и таблицы: разрешён ли `trial_3d`, как вычисляется срок и не задаёт ли `trial_7d` семь дней.
2. **RLS, ограничения и серверная валидация.** Supabase MCP был недоступен. Нужен отдельный запуск с доступом к Supabase для проверки RLS, Edge Functions, логов и advisors.
3. **Workflow-файлы не попадут в автоматический PR.** Текущий `opencode.yml` исключает `.github` из артефакта. Нужно применить `checks.yml`, `pages.yml` и строку таймаута вручную по разделу 7.
4. **CSP и SRI.** Не добавлены, потому что сайт использует встроенные стили/скрипт, Google Fonts и iframe Muuvee. Нужна отдельная политика с браузерной проверкой, чтобы не сломать видео.
5. **Pin GitHub Actions по SHA.** Сейчас действия привязаны к тегам. Для усиления supply-chain-безопасности стоит закрепить SHA после проверки версий.
6. **Юридическая проверка политики данных.** Политика описывает код, но не заменяет проверку оператора, сроков хранения и требований законодательства.
7. **Реальный E2E формы.** Нужен тестовый стенд или согласованная тестовая запись, чтобы не создавать production-заявку.
8. **Серверный honeypot и антиспам.** Клиентская защита не заменяет серверные проверки; их корректность нужно подтвердить в Edge Function.

## 6. Риски безопасности и данных

- Персональные данные родителей (имя, телефон, email, комментарий) уходят в Supabase Edge Function. Клиентская валидация не заменяет серверную; RLS и ограничения нужно подтвердить отдельно.
- Публичный publishable key ожидаем для клиентской отправки, но он не должен давать прямого доступа к таблицам. Это зависит от RLS и настроек Supabase.
- Внешние Google Fonts и iframe Muuvee получают технические данные браузера. Это отражено в политике; meta-referrer и `noreferrer` снижают объём передаваемой информации.
- Расхождение `trial_3d` / `trial_7d` может привести к выдаче неверного срока доступа, если backend трактует идентификатор как длительность.
- Политика данных снижает риск неинформированного согласия, но не гарантирует юридическое соответствие без проверки владельцем.
- Секреты в репозиторий не добавлялись. Реальные заявки, платежи, доступы и журналы не изменялись.
- Изменения в `.github` не попадут в автоматический PR и не начнут действовать без ручного применения.

## 7. Развёртывание и откат

### 7.1 Обычные изменения сайта

1. Проверить diff в PR, особенно `script.js`, встроенную копию в `index.html`, `scripts/check-site.mjs` и README.
2. Убедиться, что в PR попали `index.html`, `script.js`, `style.css`, `README.md`, `scripts/check-site.mjs`, `scripts/sync-assets.mjs` и этот отчёт.
3. Смержить PR в `main`.
4. Убедиться, что workflow `Deploy to GitHub Pages` выполнил `node --check script.js` и `node scripts/check-site.mjs`, затем опубликовал сайт.
5. После публикации открыть страницу, проверить тарифы, ссылку на политику, консоль браузера и отсутствие ошибок. Не отправлять реальную заявку без согласованного теста.

### 7.2 Ручное применение `.github` (обязательно, если автоматизация исключает каталог)

Так как текущий процесс предложения PR исключает `.github`, примените изменения отдельным обычным PR. Ниже точное содержимое нового файла `checks.yml`:

```yaml
name: Checks

on:
  push:
    branches: [main]
  pull_request:
  workflow_dispatch:

permissions:
  contents: read

jobs:
  check:
    runs-on: ubuntu-latest
    timeout-minutes: 5
    steps:
      - name: Checkout
        uses: actions/checkout@v4
      - name: Set up Node.js
        uses: actions/setup-node@v4
        with:
          node-version: "20"
      - name: Check JavaScript syntax
        run: node --check script.js
      - name: Run static site checks
        run: node scripts/check-site.mjs
```

В `pages.yml` перед шагом `Prepare site files` добавьте:

```yaml
      - name: Set up Node.js
        uses: actions/setup-node@v4
        with:
          node-version: "20"
      - name: Check JavaScript syntax
        run: node --check script.js
      - name: Run static site checks
        run: node scripts/check-site.mjs
```

В шаге `Prepare site files` замените копирование на:

```bash
test -s index.html
test -s style.css
test -s script.js
mkdir -p _site
cp index.html style.css script.js _site/
if [ -d admin ]; then cp -R admin _site/admin; fi
```

В `opencode.yml` замените строку запуска на:

```bash
timeout --signal=TERM --kill-after=30s 840 opencode run --model opencode/deepseek-v4.1-flash-free --agent build "$(cat /tmp/opencode-maintenance-prompt.txt)"
```

После добавления workflow откройте вкладку Actions и убедитесь, что `Checks` проходит на push и pull request.

### 7.3 Откат

- Изменения сайта не затрагивают базу данных, платежи, доступы и Edge Functions, поэтому откат данных не требуется.
- Откатить PR через `git revert <merge-commit>` и push в `main`; GitHub Pages переопубликует предыдущую версию.
- Если проблема только в стилях/скрипте: восстановить `style.css`/`script.js` из предыдущего коммита, выполнить `node scripts/sync-assets.mjs` и снова смержить.
- Если проблема в workflow: откатить отдельный PR с `.github` или временно отключить workflow; сайт продолжит работать, потому что стили и скрипт встроены.
- Если проблема в форме: вернуть предыдущую версию `script.js` и `index.html`; данные в Supabase при этом не удаляются и не переписываются.

### 7.4 Backend rollout для пробного тарифа

Не выполнять автоматически. Точный следующий шаг:

1. В Supabase открыть Edge Function `signup-request` и проверить, какие значения `selectedPlan` разрешены и как вычисляется срок trial.
2. Проверить таблицы заявок и доступов: сохраняется ли `trial_7d` и влияет ли он на длительность.
3. Если backend выдаёт 7 дней, подготовить явное обновление Edge Function на 3 дня с обратной совместимостью по `trial_7d`.
4. Прогнать изменение в тестовой среде или на тестовой записи, не трогая реальные заявки.
5. Раскатывать в production только после подтверждения владельца; сохранить предыдущую версию функции для отката.
6. Откат: вернуть предыдущую версию Edge Function; не удалять и не переписывать существующие заявки, доступы и журналы.
