## 3. Что исправлено

### 3.1 Автоматические проверки и публикация

Файлы: `.github/workflows/checks.yml` (новый), `.github/workflows/pages.yml`.

- Новый workflow `Site checks` запускает `node --check script.js` и `node scripts/check-site.mjs` на push в `main`, на pull request и вручную.
- `pages.yml` теперь выполняет те же проверки до `Configure Pages` и публикации.
- Если проверки падают, артефакт не готовится и публикация не выполняется.
- Используется Node.js 20, как указано в README.

Ограничение: автоматический PR исключает каталог `.github`, поэтому эти файлы нужно применить отдельным обычным PR или вручную. До применения сайт продолжит работать, но проверки перед публикацией не появятся.

### 3.2 Maintenance-workflow

Файл: `.github/workflows/opencode.yml`.

- Удалён автоматический `gh pr merge`; PR создаётся для проверки владельцем.
- Из специального UX-запуска убрана инструкция выполнять squash-слияние; добавлено требование оставить PR на проверку.
- Заголовок и тело PR больше не обещают auto-merge и не называют любую работу «UX/UI».
- `opencode run` обёрнут в `timeout --signal=TERM --kill-after=30s 840`, чтобы зависание завершалось диагностируемым кодом.
- Исправлен комментарий про `OPENCODE-REPORT.md`: файл сейчас отслеживается и не игнорируется.

Важно: текущий запуск инициирован версией workflow из `main`, поэтому его финальный шаг может ещё применить старое поведение, включая auto-merge. Новое поведение вступит в силу только после ручного применения файла.

## 5. Что осталось нерешённым и почему

1. **RLS и Edge Function Supabase.** Supabase MCP недоступен. Нельзя безопасно подтвердить ограничения доступа, серверную валидацию, rate limiting и фактическую длительность пробного доступа. Нужен отдельный запуск с доступом к Supabase.
2. **Идентификатор `trial_7d`.** Клиент сохраняет исторический ID для совместимости, хотя UI обещает 3 дня. Менять его без проверки backend нельзя: это может сломать выдачу доступа.
3. **Юридическая проверка политики.** Текст стал точнее и прозрачнее, но не заменяет проверку оператора, сроков хранения и требований законодательства.
4. **CSP/SRI.** Не добавлены: сайт использует встроенные стили/скрипт, Google Fonts и iframe Muuvee. Нужна отдельная политика с проверкой совместимости, иначе можно сломать видео или шрифты.
5. **Pin GitHub Actions по SHA.** Сейчас используются теги (`@v4`, `@v5`, `@v6`). Для усиления supply-chain безопасности стоит закрепить SHA отдельным изменением всех workflow.
6. **Реальный E2E формы.** Нужен тестовый стенд или подтверждённая тестовая запись, чтобы не создавать production-заявку.
7. **Открытые PR №6 и №7.** Это предложения предыдущих запусков; они не изменялись. Владельцу стоит проверить, не дублируют ли они этот PR, и закрыть лишние.
8. **Текущий maintenance-запуск.** Он использует старую версию workflow из `main`; до ручного применения `.github` старое поведение может сохраниться, включая auto-merge.

## 6. Риски безопасности и данных

- Персональные данные родителя (имя, телефон, email, комментарий) уходят в Supabase Edge Function. Клиентская проверка не заменяет серверную; RLS и серверную валидацию нужно подтвердить отдельно.
- Публичный publishable key в клиентском коде ожидаем для отправки формы, но он не должен давать прямого доступа к таблицам. Это зависит от RLS и настроек Supabase.
- Google Fonts и iframe Muuvee получают технические данные браузера. Это теперь явно указано в политике, но не отменяет риск сторонних сервисов.
- В репозиторий не добавлялись секреты. Статический поиск ограничен известными шаблонами и не заменяет полноценное сканирование секретов.
- Workflow-файлы улучшены, но из-за исключения `.github` из автоматического PR их нужно применить вручную. До этого текущая автоматика может сохранять прежнее поведение.
- Реальные заявки, платежи, доступы, согласия и журналы не читались и не изменялись.

## 7. Развёртывание и откат

### 7.1 Обычное развёртывание сайта

1. Проверить PR и diff, особенно `index.html`, `script.js`, `style.css`, политику данных и `scripts/check-site.mjs`.
2. Убедиться, что в PR попали `index.html`, `script.js`, `style.css` и `OPENCODE-REPORT.md`.
3. Отдельным обычным PR применить `.github/workflows/checks.yml`, обновлённый `pages.yml` и `opencode.yml`: автоматический PR исключает `.github`.
4. Смержить PR в `main`. Workflow `Deploy to GitHub Pages` выполнит `node --check` и `node scripts/check-site.mjs`, затем опубликует сайт.
5. После публикации открыть страницу и проверить: тарифы, выбор плана, ссылку на политику, отсутствие ошибок в консоли, внешний вид формы и блока видео.
6. Не отправлять реальную заявку без согласованного теста.
7. Проверить, что в GitHub Actions появился workflow `Site checks` и он зелёный.

### 7.2 Ручное применение `.github`

Так как автоматический PR исключает каталог `.github`, перенесите из этого рабочего дерева:

- новый `.github/workflows/checks.yml`;
- обновлённый `.github/workflows/pages.yml` (шаги Node и проверок до `Configure Pages`);
- обновлённый `.github/workflows/opencode.yml` (без `gh pr merge`, с shell-таймаутом и корректным текстом PR).

После применения убедиться, что:

- workflow `Site checks` запускается на push и pull request;
- `Deploy to GitHub Pages` не публикует сайт при падении проверок;
- maintenance-PR больше не сливается автоматически.

### 7.3 Откат

- Изменения не затрагивают базу данных, платежи, доступы и Edge Functions, поэтому откат данных не требуется.
- Откатить PR через `git revert <merge-commit>` и push в `main`; GitHub Pages переопубликует предыдущую версию.
- Если проблема только в стилях или скрипте: восстановить `style.css`/`script.js` из предыдущего коммита, выполнить `node scripts/sync-assets.mjs`, затем снова опубликовать.
- Если владелец хочет вернуть удалённый блок дизайн-оверрайдов: взять его из `938c2b8:style.css`, добавить в `style.css`, выполнить `node scripts/sync-assets.mjs` и отдельно проверить дизайн. Это осознанно вернёт изменения, которые были отменены предыдущим коммитом.
- Для workflow-файлов: откатить отдельный PR с `.github`. При этом не стоит возвращать auto-merge в `opencode.yml`; безопаснее оставить PR на ручную проверку.

### 7.4 Backend rollout для trial

Не выполнять автоматически. Точный следующий шаг:

1. В Supabase проверить Edge Function `signup-request`: какие значения `selectedPlan` разрешены и как вычисляется срок trial.
2. Проверить таблицы заявок/доступов: сохраняется ли `trial_7d` и влияет ли он на длительность.
3. Если backend выдаёт 7 дней, подготовить явное обновление Edge Function на 3 дня с обратной совместимостью по `trial_7d`.
4. Прогнать в тестовой среде или на тестовой записи, затем согласовать production-раскатку и откат с владельцем.

## 8. Разделение фактов и предположений

Факты: расхождение `index.html` с источниками, отсутствие `checks.yml`, отсутствие проверок в `pages.yml`, auto-merge в `opencode.yml`, отсутствие упоминаний внешних сервисов в политике, успешный проход 203 статических проверок после исправлений.

Предположения: фактическая длительность trial на backend; причина зависания из issue №2; то, что текущий дизайн без блока дизайн-оверрайдов является желаемым; полнота политики с юридической точки зрения.

## 9. Итог

Высокоприоритетные безопасные исправления выполнены и проверены локально. Русскоязычный UX, текущий дизайн, тарифы, форма, ссылки на политику и контракты с Supabase/Telegram сохранены. Главные неподтверждённые зоны — Supabase RLS/Edge Function, фактическая длительность пробного доступа и юридическая полнота политики. Для них нужен отдельный запуск с доступом к Supabase и проверка владельцем.
