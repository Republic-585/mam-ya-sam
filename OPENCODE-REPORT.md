## 0. Краткое резюме

Проверены `index.html`, `script.js`, `style.css`, `scripts/`, `README.md`, `content/` и GitHub Actions. Главные проблемы, исправленные в исходниках:

- форма не давала отдельного понятного сообщения при ограничении частоты запросов (`429`);

## 3. Что исправлено

### 3.1 Автоматические проверки и публикация

Файлы: `.github/workflows/checks.yml` (новый), `.github/workflows/pages.yml`.

- Новый workflow `Site checks` запускает `node --check script.js` и `node scripts/check-site.mjs` на push в `main`, на pull request и вручную.
- `pages.yml` теперь выполняет те же проверки до подготовки и публикации артефакта.
- Если проверки падают, публикация не выполняется.
- Используется Node.js 20, как указано в README.

Важно: каталог `.github` исключён из автоматического PR. Поэтому эти изменения нужно применить отдельным обычным PR или вручную, иначе они не попадут в предложенный PR.

## 5. Что осталось нерешённым и почему

1. **RLS и Edge Function Supabase.** Supabase MCP недоступен. Нельзя безопасно подтвердить ограничения доступа, серверную валидацию, rate limiting и фактическую длительность пробного доступа. Нужен отдельный запуск с доступом к Supabase.
2. **Идентификатор `trial_7d`.** Клиент сохраняет исторический ID для совместимости, хотя UI обещает 3 дня. Менять его без проверки backend нельзя: это может сломать выдачу доступа. Точный следующий шаг: проверить Edge Function и таблицы заявок/доступов, затем при необходимости сделать явную миграцию с обратной совместимостью.
3. **Применение workflow-изменений.** Автоматический PR исключает `.github`; без отдельного применения `checks.yml`, `pages.yml` и `opencode.yml` проверки не начнут запускаться, а auto-merge останется в действующей версии workflow.
4. **CSP/SRI.** Не добавлены: сайт использует встроенные стили/скрипт, Google Fonts и iframe Muuvee. Нужна отдельная политика с браузерной проверкой, иначе можно сломать видео или шрифты.
5. **Pin GitHub Actions по SHA.** Сейчас используются теги (`@v4`, `@v5`, `@v6`). Для усиления supply-chain безопасности стоит закрепить SHA, но это отдельное изменение всех workflow.
6. **Реальный E2E формы.** Нужен тестовый стенд или подтверждённая тестовая запись, чтобы не создавать production-заявку.
7. **Открытые PR №6 и №7.** Это предложения предыдущих запусков; они не изменялись. Владельцу стоит проверить, не дублируют ли они этот PR, и закрыть лишние.
8. **Юридическая проверка политики.** Текст стал точнее и прозрачнее, но не заменяет проверку оператора, сроков хранения и требований законодательства.

## 6. Риски безопасности и данных

- Персональные данные родителя (имя, телефон, email, комментарий) уходят в Supabase Edge Function. Клиентская проверка не заменяет серверную; RLS и серверную валидацию нужно подтвердить отдельно.
- Публичный publishable key ожидаем для клиентской отправки, но он не должен давать прямого доступа к таблицам. Это зависит от RLS и настроек Supabase.
- Google Fonts и iframe Muuvee получают технические данные браузера. Это теперь явно указано в политике, но не отменяет риск сторонних сервисов.
- В репозиторий не добавлялись секреты. Локальный поиск ограничен известными шаблонами и не заменяет полноценное сканирование секретов.
- Workflow-файлы улучшены, но из-за исключения `.github` из автоматического PR их нужно применить вручную. До этого текущая автоматика может сохранять прежнее поведение, включая auto-merge.
- Реальные заявки, платежи, доступы, согласия и журналы не читались и не изменялись.

6. Проверить, что в GitHub Actions появился workflow `Site checks` и он зелёный.

### 7.2 Ручное применение workflow-изменений

Автоматический PR исключает `.github`, поэтому ниже — точные изменения для отдельного обычного PR.

Новый файл `.github/workflows/checks.yml`:

```yaml
name: Site checks

on:
  push:
    branches: [main]
  pull_request:
  workflow_dispatch:

permissions:
  contents: read

concurrency:
  group: site-checks-${{ github.ref }}
  cancel-in-progress: true

jobs:
  check:
    runs-on: ubuntu-latest
    timeout-minutes: 5
    steps:
      - name: Checkout
        uses: actions/checkout@v4
      - name: Use Node.js 20
        uses: actions/setup-node@v4
        with:
          node-version: 20
      - name: Check JavaScript syntax
        run: node --check script.js
      - name: Run static site checks
        run: node scripts/check-site.mjs
```

В `.github/workflows/pages.yml` после шага `Checkout` и перед `Configure Pages` добавить:

```yaml
      - name: Use Node.js 20
        uses: actions/setup-node@v4
        with:
          node-version: 20
      - name: Check JavaScript syntax
        run: node --check script.js
      - name: Run static site checks
        run: node scripts/check-site.mjs
```

В `.github/workflows/opencode.yml`:

1. Заменить вызов `opencode run ...` на:

```yaml
          timeout --signal=TERM --kill-after=30s 840 \
            opencode run --model opencode/deepseek-v4.1-flash-free --agent build "$(cat /tmp/opencode-maintenance-prompt.txt)"
```

2. Удалить строки с `gh pr merge` и заменить создание PR на:

```yaml
          gh pr create --repo "$REPOSITORY" --base main --head "agent/maintenance-${RUN_ID}-${RUN_ATTEMPT}" \
            --title "chore: automated maintenance proposal (#${RUN_ID})" \
            --body "Automated audit and safe fixes from run ${RUN_ID}. The workflow ran available checks and generated OPENCODE-REPORT.md. This pull request requires owner review and is never merged automatically."
```

3. В тексте специального UX-запуска заменить требование выполнить squash-слияние на требование оставить PR владельцу и не публиковать страницу самостоятельно.

Проще всего применить эти три файла из текущего рабочего дерева: `.github/workflows/checks.yml`, `.github/workflows/pages.yml`, `.github/workflows/opencode.yml`.

### 7.3 Откат

- Изменения не затрагивают базу данных, платежи, доступы и Edge Functions, поэтому откат данных не требуется.
- Откатить PR через `git revert <merge-commit>` и push в `main`; GitHub Pages переопубликует предыдущую версию.
- Если проблема только в стилях или скрипте: восстановить `style.css`/`script.js` из предыдущего коммита, выполнить `node scripts/sync-assets.mjs`, затем снова опубликовать.
- Если проблема только в политике: откатить текст политики, но не удалять ссылки на неё; лучше исправить формулировку.
- Для workflow-файлов: откатить отдельный PR с `.github` или восстановить предыдущие версии `pages.yml`/`opencode.yml` и удалить `checks.yml`.

### 7.4 Backend rollout для trial

Не выполнять автоматически. Точный следующий шаг:

1. В Supabase проверить Edge Function `signup-request`: какие значения `selectedPlan` разрешены и как вычисляется срок trial.
2. Проверить таблицы заявок/доступов: сохраняется ли `trial_7d` и влияет ли он на длительность.
3. Если backend выдаёт 7 дней, подготовить явное обновление Edge Function на 3 дня с обратной совместимостью по `trial_7d`.
4. Прогнать в тестовой среде или на тестовой записи, затем согласовать production-раскатку и откат с владельцем.
