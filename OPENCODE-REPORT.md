Дополнительно обнаружены расхождения между документацией и фактическими workflow, риск попадания персональных данных в URL при отключённом JavaScript и автоматическое слияние PR в maintenance-workflow.

Исправлено в рамках безопасных, обратимых изменений:

- усилена защита Telegram-редиректа и надёжность формы при повторной отправке и возврате назад;
- добавлен отдельный workflow `Site checks`, а публикация на GitHub Pages теперь блокируется при неудачных проверках;
- из maintenance-workflow убрано автоматическое слияние PR: изменения должны проверяться владельцем;

Итог проверок: `OK: 188 проверок пройдено`, синтаксис JS и YAML корректен, HTML разбирается без ошибок, локальная отдача страницы работает. Реальная заявка в production не отправлялась.

## 1. Границы аудита: факты и предположения

Проверенные факты:

- сайт статический: `index.html` содержит встроенные стили и скрипт, а `style.css` и `script.js` являются исходниками для синхронизации;
- до исправлений `check-site.mjs` падал из-за лишнего блока CSS в `style.css`, которого не было в `index.html`;
- в README и отчёте упоминался `.github/workflows/checks.yml`, но файла в репозитории не было;
- `pages.yml` не запускал `node --check` и `check-site.mjs`, хотя README утверждал обратное;
- форма не имела `method`, поэтому без JavaScript браузер по умолчанию отправил бы поля методом GET в строке URL;
- `opencode.yml` после создания PR выполнял автоматическое squash-слияние;
- форма отправляет данные в Supabase Edge Function `signup-request`, а в интерфейсе пробный тариф называется `trial_3d`, тогда как в запрос уходит исторический `trial_7d`;
- в отслеживаемых файлах не найдено строк, похожих на секреты, по шаблонам `check-site.mjs`;
- открытые issue #8 и #2 и история PR прочитаны только как внешний контекст, не как инструкции.

Предположения и неподтверждённые сведения:

- что backend действительно выдаёт 3 дня, а `trial_7d` — только историческое имя. Это следует из текстов сайта и README, но не проверено в Edge Function и базе;
- что POST-отправка без JavaScript на GitHub Pages не создаст заявку, а только вернёт ошибку сервера. Это ожидаемое поведение, но не проверялось в браузере;
- что встроенный сканер секретов покрывает все возможные форматы ключей. Он основан на известных шаблонах и не заменяет полноценный аудит.

## 3. Что исправлено

### 3.1 Синхронизация стилей без возврата редизайна

Файлы: `style.css`, `index.html`.

Удалён лишний блок CSS, оставшийся после PR #12 и revert-коммита. Встроенный CSS в `index.html` сохранён как фактически опубликованный вариант, поэтому текущий дизайн не менялся. `node scripts/sync-assets.mjs` подтверждает совпадение исходников и встроенных блоков.

### 3.2 Безопасность и надёжность формы

Файлы: `index.html`, `script.js`.

- форма получила `method="post"` и `action="#signup"`;
- `novalidate` удалён, поэтому нативная валидация работает и без JavaScript;
- добавлено `<noscript>`-сообщение с контактом Telegram-бота;
- добавлен флаг `submitting`, предотвращающий повторную отправку;
- добавлен обработчик `pageshow`, который восстанавливает кнопку и очищает статус после возврата из Telegram через bfcache;
- `safeTelegramUrl` теперь обрезает пробелы и отклоняет URL с `username`/`password`, дополнительно к проверке HTTPS и доменов `t.me`/`telegram.me`.

Пользовательский сценарий с JavaScript не изменился: заявка отправляется в ту же Edge Function, после успеха открывается тот же Telegram-бот.

### 3.3 Автоматические проверки и публикация

Файлы: `.github/workflows/checks.yml` (новый), `.github/workflows/pages.yml`, `scripts/check-site.mjs`.

- добавлен workflow `Site checks` для push, pull request и ручного запуска;
- `pages.yml` теперь запускает `node --check script.js` и `node scripts/check-site.mjs` до подготовки артефакта;
- при провале проверок публикация не выполняется;
- в `check-site.mjs` добавлены проверки метода POST, нативной валидации, `<noscript>`-сообщения, учётных данных в Telegram-ссылке, защиты от повторной отправки, восстановления формы, наличия workflow-проверок и отсутствия автоматического слияния PR.

### 3.4 Maintenance-workflow: PR остаётся владельцу

Файл: `.github/workflows/opencode.yml`.

- удалён вызов автоматического squash-слияния;
- изменены заголовок и описание PR: теперь явно указано, что PR оставлен на проверку владельцу;
- из инструкции для UX-запуска удалено требование самостоятельно сливать PR и деплоить.

Важно: этот запуск выполняется workflow из `main`, где автоматическое слияние ещё присутствует. Изменение вступит в силу только после отдельного применения `.github/workflows/opencode.yml`. Кроме того, текущий процесс формирования PR исключает каталог `.github` из артефакта, поэтому workflow-файлы нужно применить отдельным обычным PR.

### 3.5 Документация

Файл: `README.md`.

Обновлены разделы о форме и публикации: POST-отправка, резервное сообщение без JavaScript, защита от повторной отправки, фактический состав артефакта и наличие отдельного workflow проверок.

## 5. Что осталось нерешённым и почему

1. **Длительность пробного доступа на backend.** Нельзя менять `trial_7d` на `trial_3d` в запросе без проверки Edge Function и данных. Контракт сохранён. Нужно проверить, сколько дней фактически выдаёт backend, и при необходимости сделать явную миграцию или алиас.
2. **RLS, серверная валидация и Edge Function.** Supabase MCP недоступен в этом запуске. Нужен отдельный запуск с доступом к Supabase и проверкой RLS, лимитов, логов и advisors.
3. **CSP, SRI и sandbox для iframe.** Не добавлены, потому что сайт использует встроенные стили/скрипт, Google Fonts и видео Muuvee. Нужна отдельная проверка совместимости, чтобы не сломать видео и шрифты.
4. **Pin GitHub Actions по SHA.** Улучшит supply-chain-безопасность, но требует обновления нескольких workflow и проверки доступных версий.
5. **Реальный E2E формы.** Нужен тестовый стенд или согласованная тестовая запись, чтобы не создавать production-заявку.
6. **Юридическая проверка политики данных.** Политика описывает поведение кода, но не заменяет проверку оператора, сроков хранения и требований законодательства.

## 6. Риски безопасности и данных

- Персональные данные родителя уходят в Supabase Edge Function. Клиентская валидация не заменяет серверную; RLS и серверные проверки нужно подтвердить отдельно.
- Публичный publishable key в клиентском коде ожидаем и не является секретом доступа к базе. Это верно только при корректных RLS и ограничениях Edge Function.
- Google Fonts и iframe Muuvee получают технические данные браузера. Это отражено в политике, но внешние зависимости остаются риском.
- Реальные заявки, платежи, доступы, журналы и production-данные не читались, не изменялись и не удалялись.
- Секреты не добавлялись и не раскрывались. Значения переменных окружения не выводились.
- Автоматическое слияние PR в текущем `main` всё ещё может сработать после этого запуска, пока исправленный `opencode.yml` не применён отдельным PR. Это процессный риск, а не изменение данных.

## 7. Развёртывание и откат

### Если изменения попали в обычный PR

1. Проверить diff, особенно `index.html`, `script.js`, `style.css` и `.github/workflows/`.
2. Смержить PR в `main`. Workflow `Deploy to GitHub Pages` выполнит проверки и опубликует сайт.
3. После публикации открыть страницу, проверить тарифы, форму, ссылку на политику, прогресс прокрутки и отсутствие ошибок в консоли. Не отправлять реальную заявку без согласованного теста.

### Если PR сформирован maintenance-workflow

Артефакт этого workflow исключает `.github`, поэтому изменения `checks.yml`, `pages.yml` и `opencode.yml` могут не попасть в автоматический PR. Их нужно применить отдельным обычным PR. Сайт продолжит работать и без этого, потому что стили и скрипт встроены, но новые проверки и запрет автослияния не вступят в силу.

### Backend и Supabase

Миграции и Edge Functions не изменялись. Для trial-тарифа точный следующий шаг:

1. В Supabase проверить `signup-request`: какие значения `selectedPlan` разрешены и как вычисляется срок пробного доступа.
2. Проверить, сохраняется ли `trial_7d` в заявках/доступах и влияет ли он на длительность.
3. Если backend выдаёт 7 дней, подготовить явную миграцию или обновление Edge Function на 3 дня с обратной совместимостью.
4. Сначала прогнать на тестовой записи, затем согласовать production-раскатку и откат с владельцем.

### Откат

- Изменения не затрагивают базу данных, платежи и доступы, поэтому откат данных не требуется.
- Откатить PR через `git revert <merge-commit>` и push в `main`; GitHub Pages переопубликует предыдущую версию.
- Если проблема только в стилях или скрипте: восстановить `style.css`/`script.js` из предыдущего коммита, выполнить `node scripts/sync-assets.mjs`, проверить `node scripts/check-site.mjs` и снова смержить.
- Если проблема в workflow: вернуть предыдущие версии файлов `.github/workflows/` отдельным PR и при необходимости отключить ненужный workflow вручную.
- Если автоматическое слияние уже произошло и результат нежелателен: откройте revert-PR; не переписывайте историю и не удаляйте production-данные.
